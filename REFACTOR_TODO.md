## 1. Цель

Превратить монолитный консольный `llao.exe` в систему из трёх частей:

1. **`llao.exe`** — существующий монолит (локальный разовый прогон). **Не изменяется**
   по поведению, остаётся в дистрибутиве.
2. **`llao-daemon.exe`** — фоновый сервер (только Windows, работает под wine без
   псевдографики). Держит очередь обработки, принимает файлы/папки на лету,
   отдаёт состояние по сети, завершается только по явной команде.
3. **`llao-cli`** — автономный кроссплатформенный клиент (Linux + Windows).
   Подключается к демону по TCP, показывает двухпанельный TUI (аналог mocp /
   Midnight Commander: слева — локальная файловая система, справа — очередь
   демона). Закрытие интерфейса (`q`) НЕ останавливает обработку; команда
   `Q` останавливает и демон. Для работы по сети клиенту не нужны никакие
   файлы проекта (модель transmission-daemon / transmission-remote-gui).

Мотивация: симулятор консоли в wine ломает псевдографику, но сам процесс
обработки и параллелизма работает корректно; большинство используемых кодеков
не имеют Linux-версий. Разделение позволяет держать движок под wine, а
интерфейс — нативным на любой платформе, плюс даёт удалённое управление.

## 2. Требования (что должно получиться)

- R1. Демон переживает отключение клиента: `q` в клиенте закрывает только UI,
  обработка продолжается; `Q` — штатная остановка демона.
- R2. Новые файлы/папки добавляются в очередь **во время** активной обработки,
  без перезапуска и без второй копии приложения.
- R3. Транспорт — TCP (HTTP/1.1, один порт). Работают любые комбинации
  «хост/клиент»: wine-демон на Linux-сервере + Windows-клиент, демон на
  Windows + Linux-клиент, всё локально.
- R4. Клиент — один самодостаточный бинарник без зависимостей от файлов проекта
  (formats/, lang/, bin/ и т.д.).
- R5. Аутентификация токеном; по умолчанию привязка к 127.0.0.1, прослушивание
  внешних интерфейсов — только явной опцией.
- R6. Веб-интерфейс (vanilla JS, без сборочных тулчейнов), ассеты вшиты в бинарник
  демона — демон остаётся одним файлом.
- R7. Передача файлов по сети: отправить файлы на оптимизацию удалённому демону
  и получить результат обратно (победитель + sidecar `.tags.zip`).
- R8. Правила AGENTS.md соблюдены: никаких хардкодов форматов/тегов/ключей/
  ограничений в C++ — всё через `formats/*.json`. Вся документация и комментарии
  для пользователя — на русском.

## 3. Карта текущего кода (результат исследования)

Бинарники и их состав:

| Бинарник | Платформа | Линкует |
|---|---|---|
| `llao.exe` | win | как сейчас, без изменений |
| `llao-daemon.exe` | win (wine) | весь движок + http_api + rpc + events + веб-ассеты; headless (всегда `no_status=true`) |
| `llao-cli` / `llao-cli.exe` | linux / win | мини-HTTP-клиент + api + screen + term_out + i18n(вшита) + fs-браузер. **Не** линкует: optimize, proc, tags, media, tool, download, config |

Обнаружение демона — файл «discovery» (атомарная запись tmp+rename):

```
%LOCALAPPDATA%/llao/daemon.json
{"port": 51234, "token": "<64 hex>", "pid": 1234, "version": "1.9.0"}
```

Под wine путь отображается в `~/.wine/drive_c/users/<user>/AppData/Local/llao/daemon.json`
— Linux-клиент на той же машине может читать его напрямую (удобно для сценария
«wine-демон + нативный клиент на одном хосте»). Порт по умолчанию 0 — ОС
выдаёт свободный. Клиент определяет адрес подключения в порядке приоритета:
флаги `--host/--port/--token` → переменные окружения `LLAO_HOST/LLAO_PORT/
LLAO_TOKEN` → discovery-файл (или `$LLAO_DISCOVERY`).

## 5. Ключевые решения и обоснование

1. **Транспорт: HTTP/1.1 поверх одного TCP-порта**, а не сырой сокет с
   JSON-lines. Причины: (а) веб-морда и передача файлов требуют HTTP — сырой
   протокол пришлось бы дублировать вторым портом; (б) это ровно модель
   transmission-daemon: команды JSON-RPC + состояние + файлы через один порт
   с одним токеном; (в) живые события — инкрементальный поллинг
   `GET /api/events?since=N` (буфер событий с монотонными seq в демоне),
   апгрейд до SSE возможен позже без смены схемы сообщений.
2. **HTTP-сервер: вендорим cpp-httplib** (`third_party/httplib/httplib.h`,
   MIT, один заголовок, чистый Winsock/Berkeley — в стиле уже вендоренных
   miniz и nlohmann). Без OpenSSL/ZLIB (дефолт). **Спайк совместимости с
   llvm-mingw+wine — день 1 фазы 1.** Fallback: собственный мини-HTTP-сервер
   (~400 строк: request line, заголовки, Content-Length, multipart не нужен
   до фазы 5) за тем же интерфейсом обработчиков.
3. **HTTP-клиент в llao-cli: самописный минимальный** (~200–250 строк,
   только сокеты): GET/POST, разбор заголовков, стриминг тела построчно,
   таймауты. Никаких библиотек — требование R4.
4. **Шов движок↔UI**: заменить прямые вызовы `status::*` на интерфейс-
   наблюдатель `obs::Sink` (те же события). Монолит получает адаптер,
   транслирующий события в `status::*` (поведение 1:1); демон — свою
   реализацию, пишущую в буфер событий + зеркало состояния.
5. **Ошибки в демоне не прерывают очередь**: семантика всей сессии демона —
   как `--ignore-errors` у монолита (файл помечается failed, остальные
   продолжаются). Обоснование: долгоживущая очередь не должна умирать от
   одного битого файла. Опцию «стоп по ошибке» можно добавить позже
   настройкой сессии. Поведение монолита не меняется.
6. **Отмена — персессионная**: структура `CancelState` вместо слепой опоры на
   глобальные атомики; глобальные остаются для монолита (Ctrl+C).
7. **Клиент автономен**: список аудио-расширений клиент получает у демона
   (`GET /api/formats`, источник — `formats/*.json`, никакого хардкода —
   правило AGENTS.md) и кэширует локально; без соединения показывает все
   файлы (демон всё равно валидирует). Локализации `lang/*.json` вшиваются
   в бинарник клиента на этапе сборки (генерируемый заголовок/translation
   unit). Резервный язык — английский.
8. **Веб-ассеты вшиты в демон**: скрипт сборки упаковывает `web/*` в zip и
   генерирует C++ translation unit с массивом байтов; распаковка в память
   через уже имеющийся miniz. Демон остаётся одним exe.
9. **`llao.exe` заморожен**: все изменения движка делаются так, чтобы
   поведение монолита было побайтово прежним (тесты + ручная проверка TUI).

## 6. Спецификация протокола управления (v1)

Все тела — UTF-8 JSON. Авторизация на всех эндпоинтах, кроме `GET /`
(страница логина): заголовок `Authorization: Bearer <token>`, иначе `401`.

### 6.1. Команды

`POST /rpc` — тело `{"cmd": "...", "args": {...}}`; ответ
`{"ok": true, "result": {...}}` либо `{"ok": false, "code": "...", "error": "..."}`.

| cmd | args | результат / примечания |
|---|---|---|
| `ping` | `{}` | `{version, uptime_s, queue:{total,done,failed}}` |
| `stat` | `{paths:[...]}` | существование/тип путей **на стороне демона** (для режима локальных путей) |
| `add` | `{paths:[...], recursive?:true}` | `{added:[{id,label}], rejected:[{path,reason}]}`; пути резолвятся на стороне демона; дедуп против уже стоящих в очереди; события `added` в буфер |
| `cancel-file` | `{id}` | пометить файл отменённым; если ещё не в prep — сразу skip |
| `cancel-all` | `{}` | мягкая остановка: не запускать новые задачи, дождаться активных; следующий `add` снимает остановку |
| `shutdown` | `{force?:false}` | graceful: дождаться активных файлов, финализировать, убрать discovery-файл, exit 0; `force` — убить активные процессы |
| `formats` | `{}` | `{formats:[{id, extensions:[...]}, ...]}` — источник истины `formats/*.json` |

Зарезервировано на будущее (не реализовывать в v1 без нужды): `set-options`,
`pause`/`resume`.

### 6.2. Состояние и события

`GET /api/state` — полный снимок (для подключения «на ходу» и поллинга):

```json
{
  "version": "1.9.0",
  "session": {"started_at": "2026-08-21T12:00:00Z",
               "options": {"jobs": 16, "verify": "strict", "dry_run": false}},
  "counters": {"total": 120, "done": 45, "failed": 2},
  "last_seq": 1042,
  "rows": [
    {"id": 0, "label": "rel/path.flac", "state": "ok", "pct": 12.3,
     "tasks": ["ok", "ok", "failed"]}
  ]
}
```

Состояния строки: `queued | prep | running | ok | skip | error` — выводятся
из полей `FileJob` (`prep_done/done/any_passed/mark_*`); маппинг должен быть
единым для снимка и событий.

`GET /api/events?since=N` — события с `seq > N` (до 1000 за ответ) +
`{"events":[...], "last_seq": M}`. Типы событий — зеркало `obs::Sink`:

```
begin_file{id,label} prep{id} set_tasks{id,total}
task{id,idx,state:"running|ok|failed"} end_file{id,pct}
skip{id} error{id|null,line} log{line}
added{id,label}            — пополнение очереди
stopped{} resumed{}        — cancel-all / снятие остановки
shutdown{}
```

Буфер событий: deque с монотонным `seq`, ёмкость 10 000 (при переполнении —
вытеснение старых; клиент, отставший сильнее, получает в ответе флаг
`resync:true` и обязан перечитать `/api/state`).

`GET /api/formats` — то же, что rpc `formats` (нужен браузеру и TUI).

### 6.3. Передача файлов (фаза 5)

- `POST /files/upload` — multipart, поля `file[]` + `relative_path[]`;
  опциональный заголовок `X-SHA256` для проверки целостности (sha256 уже есть
  в проекте — `src/sha256.h`). Ответ `{ticket:"<uuid>"}`.
- Файлы кладутся в `inbox/<ticket>/` рядом с exe, тикет автоматически попадает
  в очередь с метаданными `origin:"upload"`; победитель и sidecar пишутся
  обратно в каталог тикета.
- `GET /api/results/<ticket>` — манифест
  `{state, files:[{name,size,sha256,url}]}`.
- `GET /results/<ticket>/file?name=...` — скачивание (имя санитизируется:
  только basename, разрешённые имена из манифеста; защита от path traversal —
  обязательно).
- Политики: лимит размера файла (по умолчанию 2 ГБ), квота inbox (по умолчанию
  20 ГБ → `507`), retention результатов (по умолчанию 24 ч или «стереть после
  скачивания»), поток-уборщик по таймеру.

### 6.4. Семантика путей `add`

- По умолчанию пути трактуются как **локальные для демона** (главный сценарий:
  общий диск/та же машина). Демон проверяет существование (`stat`) и внятно
  отвечает в `rejected[].reason`.
- Если путь не найден на стороне демона, ответ содержит подсказку использовать
  загрузку (фаза 5: `--upload` в CLI, кнопка в TUI/вебе).

### Фаза 1 — демон

Цель: `llao-daemon.exe serve` — headless-движок с HTTP-API, пополнением
очереди на лету и штатным выключением.

Чеклист:

- [ ] Спайк (день 1): вендорить `third_party/httplib/httplib.h`, собрать
      минимальный сервер, проверить под wine + llvm-mingw (GET/POST, keep-alive).
      Fallback-решение принять до начала остальных работ (§5.2).
- [ ] `src/events.h/.cpp`: `EventBuffer` (mutex + deque `{seq, json}`,
      ёмкость 10 000, `push(type,args)`, `copy_since(n)`, флаг `resync`)
      и `StateMirror` — зеркало строк очереди (аналог модели `Row` из
      status.cpp, но без отрисовки), обновляется демоном-синком.
- [ ] `src/daemon_sink.cpp`: `obs::Sink`-реализация демона → EventBuffer +
      StateMirror (+ зеркалирование log/error в файл-лог).
- [ ] `src/rpc.cpp`: диспетчер команд §6.1 — **платформонезависимый** файл
      (только json + ссылки на Runner/EventBuffer), чтобы юнит-тестировать
      нативно в CI.
- [ ] `src/http_api.cpp`: обработчики httplib — авторизация Bearer,
      `/rpc`, `/api/state`, `/api/events`, `/api/formats`; mount статических
      ассетов (фаза 4).
- [ ] `src/serve.cpp`: команда `serve`:
      - флаги: `--bind` (default 127.0.0.1), `--port` (default 0=auto),
        `--discovery PATH`, плюс опции optimize как дефолты сессии
        (`--jobs`, `--verify`, `--dry-run`, `--no-stats`, `--debug`, ...);
      - генерация токена (32 случайных байта hex; BCryptGenRandom /
        CryptGenRandom), атомарная запись discovery-файла;
      - `config::load_all()` при старте (fail fast);
      - Runner создаётся лениво при первом успешном `add` (общий код
        подготовки вынести из `run()` в хелпер, используемый обоими);
        пул воркеров стартует один раз и живёт до shutdown;
      - поток-монитор: ждёт `all_done && !scan_pending` → выполняет
        «хвост» `run()` (сводки, отчёт `--report`, stats, чистка tmp),
        вырезанный в функцию `finalize_run(Runner&)`, и засыпает до новых
        добавлений;
      - graceful shutdown: прекратить приём → дождаться активных файлов
        (или `force`: session cancel + `abort_all`) → `finalize_run` →
        удалить discovery-файл → exit 0;
      - файл-лог `llao-daemon.log` рядом с exe, ротация ~5 МБ (переименовать
        в `.1`).
- [ ] Политики tmp: каталог сессии на каждый «батч»; при старте подчищать
      осиротевшие `tmp/*` (без lock-файла и старше N часов).
- [ ] Поведение `cancel-all`/`add` по §6.1 (остановка мягкая, `add` снимает).
- [ ] Wine-специфика: протестировать сценарии «запуск в wineconsole и
      закрытие окна», «`wine start /b`», работу при недоступном stdin.
      Задокументировать рекомендуемый способ фонового запуска в README.

Критерии приёмки:

- Под wine: демон стартует, пишет discovery, отвечает на `ping`.
- Сквозной тест (см. §9): add → события с монотонными seq → состояние
  `ok` → shutdown, discovery удалён, exit 0.
- Второй `add` во время активной обработки принимается и обрабатывается
  (ключевое требование R2) — повторяемый стресс-подтест.
- Запрос без/с неверным токеном → 401.

## 10. Риски и способы закрытия

| Риск | Закрытие |

## 13. Как работать (памятка исполнителю)

1. Сначала прочитать AGENTS.md (запрет хардкодов форматов/тегов/ключей,
   релизный процесс, русский язык документации) и файлы из §3.
2. Двигаться строго по фазам; каждая фаза = зелёная сборка + тесты +
   коммит(ы) по пунктам чеклиста.
3. Поведение `llao.exe` заморожено: после каждой фазы прогонять
   `tests/test_tags.py`, `tests/test_errors.py` и ручной TUI-прогон.
4. Не трогать `formats/*.json` без необходимости; любые новые строки UI —
   через lang/*.json (i18n), не строковыми литералами в C++.
5. Перед созданием релизного тега `v*` — перенести выполненное в «Сделано»
   TODO.md, обновить README.md (новые команды serve/attach/send, правила
   безопасности, wine-запуск демона), сверить CLI-эталоны.
