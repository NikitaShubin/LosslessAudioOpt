# Контракт web-клиента и публичных событий демона

Слепок на 2026-09-06 (Фаза 0), актуализирован после Фазы B (каноническая
событийная модель). Сверяется по `tests/golden/events-*.jsonl` и `.types`.

## Web-клиент (web/app.js)

UI **не потребляет** `/api/events`. Вся отрисовка строится на поллинге
`GET /api/state` (в `pollState()`). Одна динамическая точка — `rpc()` POST
`/rpc`.

### Поля строки из `/api/state` rows (по использованию в app.js)

- `id`, `label`, `state`, `pct` — базовое состояние строки
- `tasks`, `task_infos` — состояния и метаданные вариантов
- `excluded` — форматы, исключённые по caps
- `mode` (optimize|restore) и `out_path` (фактический результат)

Пауза/перезапуск вычисляются из `state` (`queued|prep|running|stopped|error`),
кнопки перезапуска — только для `stopped`/`error`.

### Команды RPC (и аргументы)

- `add` {paths, recursive, target_dir} — отправка файлов
  (recursive — всегда true в данный момент; целевая папка из формы). target_dir
  действует для обоих режимов: optimize и restore пишут результат в
  `<target_dir>/<rel-подкаталог пачки>/` (rel пуст для одиночного файла),
  исходник остаётся на месте; пусто = замена на месте. В optimize при заданной
  целевой папке в цель пишется даже кандидат, не меньший исходника (лучший из
  прошедших валидацию); `out_path` строго внутри target_dir.
- `reorder` {order}
- `remove` {id}
- `cancel-file` {id}
- `restart` {ids}
- `bulk-cancel` {ids}
- `bulk-remove` {ids}
- `cancel-all` {} — останавливает ВСЕ активные файлы очереди на стороне демона
  (список id не передаётся: работает даже при устаревшем состоянии вкладки),
  возвращает `{cancelled}`; дополнительно ставит очередь на паузу.
- `clear-done` {}
- `pause` {} / `resume` {} — только пауза/возобновление запуска новых задач,
  активные процессы не прерывает.
- `sort` {}
- `shutdown` {}

## Публичные события `GET /api/events?since=N`

Каноническая модель (Фаза B): событие = `{type, seq}` + инлайновые поля
payload + `id` (связь со строкой очереди) для всех file-событий. Поля `id`
в payload эмиттеры НЕ дублируют: id приходит из канонической привязки
Event.file_id. Обёртки `args` нет — все поля в корне JSON.

Типы (поля без seq/type; `id` — стабильный idx строки):

- `added` {id, label} — новая строка добавлена в очередь
- `begin_file` {id, label} — строка создана (начало обработки файла)
- `job_meta` {id, mode, target_dir} — режим/целевая папка строки
- `prep` {id} — строка взята в обработку (prep)
- `set_tasks` {id, task_infos, total} — набор метаданных задач
- `set_excluded` {id, excluded} — форматы, исключённые по caps (жёлтые точки)
- `task` {id, idx, state} — состояние варианта (running|ok|failed)
- `state` {id, state} — смена состояния строки
- `end_file` {id, pct} — файл завершён (ok), pct — выигрыш
- `out_file` {id, path} — фактический путь результата (restore/замена на месте)
- `error_file` {id, reason} — файл завершился ошибкой (одно событие на ошибку)
- `error` {line} — глобальная строка ошибки, не привязана к файлу
- `log` {line} — строки журнала движка
- `removed` {id} — строка удалена
- `reordered` {order} — применён порядок
- `resumed` {} — очередь возобновлена
- `stopped` {id?} — одна схема: {id} для остановки строки (cancel-file),
  {} для паузы всей очереди (pause)

### Гарантии порядка (Фаза B)

1. Для каждого файла события `begin_file`, `job_meta`, `added` эмитятся под
   qm-локом append_files — строго до любого `prep`/`task`/`state` этого файла.
   Воркер не может выпустить вариант, пока не владеет qm.
2. `set_tasks`/`set_excluded` эмитятся воркером prep под qm, до
   `cv.notify_all()` — строго раньше первого `task(running)` файла.
3. Порядок для нового файла: `begin_file -> job_meta -> added -> prep ->
   set_tasks -> task(running) -> state(running) -> ... -> task(ok/failed) ->
   end_file` (+ `out_file` в restore). После `end_file` новых `task`/`state`
   нет.
4. Ошибка файла — ровно одно `error_file {id, reason}` на ошибочный файл
   (было: `error {line}` + `error {id}` из двух источников).
5. Удаление строки (`remove`/`bulk-remove`/`clear-done`) — терминальное:
   ровно одно `removed {id}`. После него события по этому `id` НЕ публикуются
   даже если воркер ещё дорабатывает снятый кандидат: зеркало томбирует id
   (`StateMirror::remove`), а `DaemonSink::emit()` подавляет запоздалые
   `task`/`state`/`end_file`/`error_file` удалённой строки. `seq` остаётся
   контигуальным (подавленные события не получают seq).

## Изменения Фазы A (сверка контракта)

- `recursive` удалён из `add` целиком (обход всегда рекурсивный); web-форма
  без галочки «рекурсивно».
- `mode`/`target_dir` теперь строго строки: неверный тип — `bad_args` (было
  тихое дефолтное значение).
- `--restore-to` валидируется при старте демона и в `add_locked` —
  неизвестный формат отклоняется (было: ok с 0 задачами).
- Пути нормализуются (`\`→`/`, без хвостовых разделителей) до дедупа.

## Изменения Фазы B (единая событийная модель)

- `dsvc::Event` канонизирован: `{seq, type, has_id, file_id, payload}`;
  эмиттеры файловых событий используют `EventBuffer::push_for(id, ...)` —
  `id` больше не кладётся вручную в payload.
- Гонка «task(running) до begin_file» устранена: события добавления эмитятся
  внутри qm-lock до `cv.notify_all()` (append_files).
- Гонка «task(running) до set_tasks» устранена: set_tasks/set_excluded
  эмитятся воркером под qm до notify (см. optimize.cpp).
- Единая модель ошибки: `obs::Sink::error_file(id, reason)` вместо пары
  `error(line)` + `mark_error(id)`. Монолит (StatusSink) сохраняет вывод
  байт-в-байт: error_file = печать строки в stderr + красная полоса.
- `init_session()` удалён из `obs::Sink` (движок его никогда не вызывал).
- `job_meta` эмитится симметрично и в init-пути движка (одноразовый прогон);
  демон стартует с пустым initial_inputs, поэтому канонических событий это
  не добавляет.
- Единый `TaskState`: дубликат `status::TaskState` удалён, осталась
  `obs::TaskState` (alias в status).
- `mark_error(id)` в демоне — запасной путь: ставит state=error без события
  (ревёрс событий после Фазы B не вносит двойных error_file).
- Tombstone и «призрачные» события: после `removed` id томбирует в `StateMirror`,
  все файловые события фильтруются через `alive(id)` (DaemonSink::emit) —
  запоздалые события воркера не воскрешают строку и не уходят в буфер.
  Прямые push "removed"/"stopped" из DaemonSession терминальные и эмитятся
  намеренно.
