# LLAO — Lossless Audio Optimizer. План и дальнейшие действия

> Документ на русском. Здесь — принятые решения, текущий статус и **дальнейшие действия**.
> Описание конечного состояния проекта — в `README.md`. Код пишется только после согласования
> этого плана.

## 1. Решения (согласовано с пользователем)

1. **Стек — C++/Windows.** Проект — Windows-native приложение на C++17, компилируется в единый
   `llao.exe` (кросс-компиляция MinGW-w64). На Linux запускается под `wine`. Python-реализация
   `llao/` и `scripts/` удаляется.
2. **Внешние JSON-конфиги остаются.** Форматы описываются в `formats/*.json` и читаются exe на
   лету (расширяемость без пересборки). Для C++ используются `nlohmann/json` и `miniz` — уже в
   `third_party/`.
3. **Только Windows-версии кодеков.** Linux-версии в конфигах не нужны: на Linux всё работает
   под wine, поэтому скачиваются только `os: "windows"`/`"any"` записи.
4. **Теги — групповая модель**: каждый формат тегов (ID3v2, RIFF, Vorbis, APEv2, ID3v1, MP4)
   хранится как отдельная группа и встраивается, если целевой формат поддерживает её тип, иначе
   — в ZIP-sidecar; стоимость кандидата = файл + sidecar.
5. **Исходные файлы заменяются на месте** после полной валидации победителя.
6. **Полный перебор**: время не ограничено, покрываются все форматы и варианты из конфигов.
7. **Параллельность**: процесс на файл; `--jobs 0` (по умолчанию) = число доступных ядер.
8. **Статистика накапливается внутри ПО** (п. 2 ниже) — для будущего ранжирования форматов.
9. **Конфиг сверяется с реальной версией утилиты** (п. 3 ниже) — контроль устаревания.
10. **Скачивание**: основной путь — встроенный WinHTTP (HTTP/HTTPS, TLS); при неудаче под wine
    — fallback на внешний `curl.exe`, затем ошибка.
11. **ffmpeg.exe** — свежие сборки BtbN (`win64-gpl`), скачиваются при первом запуске.
12. **`--min-savings` отклонён.** Микровыигрыш (<0.05%) учитываем: система предназначена
    только для хранения аудио; воспроизводимость результата — желательна, но не обязательна.
13. **Вместо `--min-savings` — команда `restore`** (обратная оптимизация): декод
    оптимизированного файла → пережатие в целевой формат (по умолчанию FLAC) → прикрутка
    тегов обратно (embedded или из `.tags.zip`).
14. **Повторная оптимизация оптимального файла ничего не меняет** (условие `best_cost <
    probe.size` уже это обеспечивает) — покрыть тестом.

## 2. Статистика (накапливается, для будущего ранжирования)

- Пополняется **автоматически** при каждом использовании ПО (без действий пользователя),
  хранится в JSON-файле `stats.json` **рядом с exe**.
- На каждого кандидата записывается: файл (размер, параметры аудио: битность/каналы/частота/
  длительность), исходный формат и размер, формат+вариант сжатия, размер результата,
  суммарный размер (файл + sidecar), время кодирования, статус (ok/error/pruned), был ли
  кандидат победителем.
- Сейчас эта статистика **накапливается и используется**: при `optimize` форматы
  перебираются в порядке ранжирования — наиболее вероятные победители первыми (средняя
  экономия по успешным кандидатам; lossy-источники в оценке не участвуют). Команда
  `llao.exe stats` показывает текущее ранжирование.

## 3. Контроль соответствия конфига версии утилиты

- Проблема: при скачивании «последней» версии кодека параметры могли добавиться/удалиться,
  и `variants` в конфиге могут перестать соответствовать реальному CLI.
- Предложение: в конфиг добавить поле `cli_check` (например `{ "cmd": ["--help"], "expect":
  ["--preset", "--md5", ...] }`) — список ключевых подстрок, которые обязаны присутствовать
  в выводе утилиты. При подготовке утилиты вызвать её с `--help` и проверить наличие; при
  несовпадении — пометить конфиг как «возможно устарел» и сообщить пользователю (не блокируя
  работу, но с явным предупреждением и логированием).
- Решение: храним **список ключевых опций**. На практике (шаг 5.2) надо проверить, что такой
  подход действительно отлавливает изменения параметров между версиями.

Известные ограничения проверки под wine:

- **LA** — работает headless: `La04b.exe` (NSIS-установщик) обрабатывается через
  `kind: extract7z`, из него забираются только `la.exe`+`la-core.dll` (winamp-плагины и
  установка в систему не требуются). Кодер медленный, только моно/стерео 16-бит PCM.
  `optimize`/`restore` не могут принять `.la`/`.ofr` как **источник**: проба идёт через
  ffprobe, который не знает формат LA (и OFR-демуксера нет в BtbN-сборках) — такие
  файлы попадают в SKIP. Декод LA (encode→decode, MD5-идентичен) проверяется нативным
  вызовом `la.exe`.
- **Monkey's Audio**: сайт monkeysaudio.com дросселирует скачивание (~800 Б/с, 2.3 МБ —
  десятки минут; таймаут WinHTTP увеличен до 600 с, но даже он может не успеть).
  Если инсталлятор `x64.exe` уже есть в `bin/monkeys_audio/` (кэш), перекачивания нет;
  `MAC.exe`+`MACDll*.dll` извлекаются из него через 7-Zip без установки.
- **MPEG-4 ALS**: кодер `mp4als` удалён из современных сборок ffmpeg (остался только
  декодер), поэтому `mpeg4_als` остаётся `enabled: false` фактически нерабочим.
- **OptimFROG** не принимает «голый» синтетический WAV без LIST-чанка — на реальных
  файлах (из FLAC и т.п.) работает корректно.
- **ffmpeg/ffprobe (BtbN) не содержит OFR-демуксера** — валидация тегов OptimFROG
  выполняется нативным чтением APEv2-хвоста (не ffprobe); сторонние программы читают
  теги .ofr по стандарту APEv2.
- **wavpack `-x6` недетерминирован**: одинаковый вход кодируется в файлы с разницей до
  ~100 байт (проверено под wine; `-x0` детерминирован). Это свойство утилиты, не наш баг —
  поэтому размер кандидата может «дрожать» между запусками на десятки байт.
- **ffmpeg vs нативный декодер (wavpack) — расхождения НЕТ**: разница в md5/размере
  декодированных WAV объясняется только WAV-заголовками (wvunpack пишет LIST-чанк 132 Б,
  ffmpeg — 26 Б → смещение data-чанка). По `data`-чанку все декоды идентичны
  (`5b415cae…` = STREAMINFO MD5 исходника). Тем не менее декод источника нативным
  декодером формата сохранён — это референсное поведение и защита от контейнерных
  нюансов чужих декодеров.

### 5.1 C++-модули и сборка
1. `src/`: `util` (пути/файлы, UTF-8↔UTF-16, поиск в PATH), `sha256`, `config` (загрузка и
   валидация `formats/*.json`), `proc` (CreateProcess: захват вывода, таймаут, завершение),
   `download` (WinHTTP: HTTP/HTTPS, редиректы, таймауты), `archive` (zip через miniz, защита от
   path traversal), `tool` (кэш `bin/<id>/` → PATH → скачивание + SHA-256 + распаковка +
   копирование `.exe` + сверка `cli_check`), `stats` (запись статистики), `main.cpp` (CLI).
2. `Makefile` для MinGW-w64 (`-std=c++17 -static`, `-lwinhttp`).
   — Сборка: `export PATH="$HOME/opt/llvm-mingw-<ver>-…/bin:$PATH"; make` (обёртки
   `x86_64-w64-mingw32-g++/gcc` из llvm-mingw; системный пакет mingw-w64 не требуется).
3. Сборка `llao.exe`.
   — Сделано: собрано, работает под wine.

    `--jobs 0` = число ядер, замена исходника на месте, ведение статистики.
18. **Валидация победителя**: декод → побайтово против эталона; сверка всех тегов.
19. **Отчёты**: JSONL-лог, итоговый отчёт (таблица форматов, экономия, причины исключений).
    — Сделано: `report.{h,cpp}` (JSONL-журнал `runs/llao-<ts>.jsonl`, итоговый отчёт
    `--report=<файл|каталог>`, события run/file/candidate/file_done), статистика всех
    кандидатов в `stats.json` (в т.ч. пропущенных/ошибочных), `stats::append_all`.
20. **Тесты и полировка**: таймауты, обработка сбоев сети/кодеков, документация.
21. **Надёжность** (Этап 3): уникальный префикс временных файлов в `tmp/` (коллизии при
    одинаковых base_name из разных папок при `--jobs>1`), мьютекс на `tool::ensure`
    (параллельный первый запуск ffmpeg-кэша), команда `restore` (см. решение 13), тест
    повторной оптимизации оптимального файла (см. решение 14).
    — Сделано: `tmp_token()` (FNV-1a 64, hex-префикс) в `optimize`; `g_ensure_mutex` +
    двойная проверка в `tool::ensure`; `restore_run()` + `tags::read_sidecar()`;
    `lower_ext()`/`find_source_fmt()` для декода источника нативным декодером (без
    скачивания — только кэш/PATH, fallback ffmpeg); `cmd_restore` в main. Проверено
    полностью (см. разд. 4).
22. **Lossy-входы** (Этап 4): флаг `--allow-lossy` — разрешить/пропускать обработку lossy.
    — Сделано: `media::codec_is_lossless()`/`Probe::is_lossless()`, флаг в `optimize`/`restore`,
    SKIP с сообщением без флага. Проверено на mp3 и webm.
23. **Ранжирование форматов** (Этап 5): по накопленной статистике строить порядок
    кодирования (наиболее вероятные победители первыми).
    — Сделано: `stats::ranking()` (средняя экономия по успешным кандидатам, lossy-источники
    исключены), сортировка форматов в `optimize`, таблица ранжирования в `llao.exe stats`.
    Проверено на реальном прогоне и на mp3-входе (не искажает оценки).

Найденные и исправленные баги (важно для будущего):

- Краш `_Rb_tree_increment` в `probe_file` — итерация по `.items()` временного nlohmann-объекта
  (`fmt.value("tags", json::object())`): висячий итератор. Лечится локальной переменной.
- FLAC `METADATA_BLOCK_PICTURE`: после описания нужно `pos += 16` (width/height/depth/colors),
  а не 12 — иначе `blen` читает поле `colors` (=0) и картинка теряется.
- `apev2_parse`: заголовок APEv2 определяется по `memcmp(items, "APETAGEX")` и `items += 32`,
  а не проверкой за 32 байта ДО `items`.
- `id3v2_parse`: возврат стандартных текстовых фреймов (TIT2/TPE1/TPE2/TALB/TCON/TDRC/TRCK/
  TPOS/…) и всех TXXX (BPM, TRACKTOTAL и т.п.) — до этого терялись TPE2/TPOS/TXXX-поля.
- `optimize`: sidecar писался только при «ошибке встроенной записи»; при «caps не покрывают всё»
  `terr` оставался пустым и sidecar НЕ создавался (теги молча терялись). Логика переписана.
- Замена на месте оставляла старое расширение (tak-контент в `.flac`); теперь файл
  переименовывается в расширение победителя.
- ffprobe не читает APEv2 у `.wv` (только у `.ape`), поэтому валидация wavpack-тегов идёт
  нашим нативным парсером — она проходит, теги сохраняются.
- `write_embedded` падал с «не поддерживает встроенные теги» для форматов без встроенной
  записи даже при ПУСТОМ наборе тегов (файл без тегов) — теперь пустой TagSet — no-op успех.
- Встроенные теги OptimFROG не писались: APEv2-ветка в `write_embedded` проверяла `fmt_id
  == "ofr"`, а в конфиге id = `optimfrog`. Добавлено. Плюс `validate_tags` для ofr читает
  записанные теги напрямую из APEv2-хвоста (в ffprobe BtbN нет OFR-демуксера).
- `read_sidecar` искал `<путь>.tags.zip`, но оптимизация сохраняет sidecar как
  `<имя без расширения>.tags.zip` — restore «терял» теги (теги молча не восстанавливались).
  Теперь пробуются оба имени.
- Лимит 60 с на кодирование LA (наследие GUI-обхода) убран — `la.exe` теперь CLI-кодер,
  использует стандартный таймаут 1800 с.
- **Windows-прогон**: `ftp.osuosl.org` не отдаёт flac (WinHTTP 12029 / curl 35 — обрыв
  SSL-handshake) — URL заменён на официальный GitHub-релиз xiph/flac (тот же zip, тот же
  SHA-256 `53f1500f…`). Маркер кэша `.binary` мог быть записан другой ОС (wine → `Z:\…`,
  невалиден на Windows и наоборот): `cached_binary` теперь делает fallback по имени файла
  в `bin/<id>/` — общий кэш переносим между wine и Windows (на Windows ffmpeg из-за этого
  подменялся `C:\Windows\system32\ffmpeg.exe` из PATH). Дублирование `[id] [id]` в сообщении
  об ошибке   скачивания убрано.
- **Краш `libc++abi: terminating … __wide_to_char: Illegal byte sequence`** на файлах с
  не-ASCII именами (например, кириллица): libc++ (llvm-mingw) `std::filesystem` конвертирует
  wide→narrow через ANSI-кодовую страницу при не установленной локали ("C"), поэтому
  `path::string()`/`fs::path(utf8)` падали. Все операции переведены на
  `fs::u8path()`/`path::u8string()` (util, archive, config, optimize, tool, download, report)
  — пути всегда UTF-8, независимо от локали. Проверено под wine: папка и файл с кириллицей и
  спецсимволом (`Тестовая запись №1.wav`) → probe/encode/замена на месте/restore, PCM
  побайтово совпадает. В `main()` добавлен try/catch — вместо аварийного завершения
  выводится «ОШИБКА: …».

Ограничения (проверено):

- **TAK**: ffmpeg (`tak demuxer`) не декодирует `.tak` с ID3v2-префиксом — встроенные теги
  для tak отключены (`capabilities: false`), теги идут в sidecar (это не мешает декоду,
  кандидат валидный).
- **ALAC/MP4**: ReplayGain в M4A не пишется (caps `replay_gain: false`) → sidecar.
- **OptimFROG**: встроенные APEv2-теги пишутся и валидируются нативно (ffprobe BtbN без
  OFR-демуксера) — сторонние программы читают их по стандарту APEv2.
- **MPEG-4 ALS**: кодер `mp4als` удалён из ffmpeg → `enabled: false`.
- Потерянных форматов (webm с видео, mkv) — файл пропускается по наличию видеопотока.
- Lossy-входы (mp3 и т.п.) по умолчанию пропускаются; с `--allow-lossy` конвертируются
  в lossless (размер при этом растёт — см. Этап 4, п. 22).

Дальнейшее: все этапы плана (пп. 1–23) выполнены и проверены. Возможные улучшения —
ранжирование вариантов внутри формата, порядок по типу контента (см. разд. 2).

## 7. Роль ffmpeg

1. **Декод произвольных входных форматов** в эталонный WAV (`*.* → *.wav`): mp3, aac/m4a,
   ogg/opus, webm, wma, flac, wavpack и т.д. Это основа конвейера — все кодеры работают от
   эталонного PCM, а lossy-исходник сам участвует в сравнении.
2. **Встроенные lossless-кодеры** для форматов без своей Windows-утилиты: ALAC, TTA,
   MPEG-4 ALS (`-c:a alac|tta|mp4als`).
3. **ffprobe** — анализ параметров файла (формат, кодек, битность, каналы, частота, длительность).

Наши 9 форматов кодируются/декодируются **нативными утилитами** из конфигов (лучшее сжатие,
полные теги, MD5; ffmpeg не кодирует LA/OFR/TAK/APE). Теги ffmpeg не обрабатывает — этим
занимается отдельный тег-модуль.
